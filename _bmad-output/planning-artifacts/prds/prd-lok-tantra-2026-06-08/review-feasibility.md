# Adversarial Review — Technical Feasibility / Buildability

## Overall verdict
The PRD is solid as a product spec — vision, journeys, neutrality guardrails, and FR/UJ traceability are unusually clean and ready for UX work. But two of its three headline capabilities (FR-7 continuous Time Travel to 1947, and the data underneath it) rest on assumptions the codebase actively contradicts: there is no `Tenure`-shaped data model, no historical political dataset (the newly-added `seed-political.ts` is exclusively *current*, 2024-on data), and no precedent anywhere in the stack for date-driven graph re-rendering at the scale FR-7 implies. Architecture should not be allowed to start epic-cutting until Open Question #3 is answered with an actual data audit — as scoped, FR-7 is closer to "build a new national historical-records project" than "add a feature to LokTantra."

## Findings

- **critical** FR-7's core data model ("Tenure") does not exist in the schema, and the closest analogues are general-purpose role records, not an Office-occupancy abstraction (§4.4, §3 Glossary "Tenure", FR-7) — The Glossary defines **Tenure** as "the atomic unit that makes Time Travel possible," but `prisma/schema.prisma` has no `Tenure` model. The nearest things are `PersonRole` (`personId`, `institutionId`/`committeeId`, `title: String`, `validFrom`/`validTo`) and `PersonPartyHistory` (`validFrom`/`validTo`). Neither is keyed to a stable `Office` entity the way the Glossary's "Tenure = Person × Office × date range, atomic unit of resolution" demands — `Position` (the closest "Office" analogue) carries only a `currentHolderId` (a single nullable 1:1 relation, line 322 `currentHolderId String? @unique`) with **no history table at all**. Building FR-7 means designing and migrating a new `Office`/`Tenure` schema from scratch, including how an `Office` itself comes into/out of existence (Offices "established"/"abolished" — see next finding) — this is schema-design and migration work the PRD presents as a given ("the atomic unit that makes Time Travel possible") rather than as build scope. *Fix:* Add an explicit FR or architecture-handoff note: "Design and migrate an Office/Tenure data model (does not currently exist); audit `Position`/`PersonRole`/`PersonPartyHistory` for reuse vs. replacement" — and surface this as a prerequisite gating FR-7, not an implementation detail architecture will "just figure out."

- **critical** FR-7's "last known state" rule and "not yet established" consequence are under-specified for the actual hard cases an engineer will hit (§4.4, §3 Glossary "Time Travel", FR-7 consequences, Open Question #5) — The rule "most recent Tenure-start at or before the selected date" is clean for offices that exist continuously with clean successions, but the PRD doesn't specify: (1) what counts as a "known transition" when historical sources conflict or only give a year, not a date (extremely common pre-1990s — e.g. "took office in 1977" with no day/month) — does the resolver treat `1977-01-01` as the transition date, and if so, what does the UI show for "as of 3 March 1977" when the true transition might have been in July? (2) What happens for an Office that existed, was abolished, and was later **re-established** (e.g. Planning Commission → NITI Aayog is a replacement not a continuity, but some ministries have literally been split/merged/renamed across decades) — is that one `Office` row with gaps, or two `Office` rows, and how does "last known state" resolve a query landing in the gap? (3) The PRD says offices that "did not yet exist" must be "visibly absent or marked 'not yet established'" but doesn't define the *boundary condition*: an Office established on 26 January 1950 queried on 25 January 1950 — is that "not yet established" (binary existence flag) or does the resolver fall through to "last known state" and show nothing? Open Question #5 asks whether the data model can distinguish "vacant" from "not yet established" but doesn't ask the harder question: who/what authoritatively timestamps an Office's *existence* (vs. its occupancy), and is that data sourced or assumed? *Fix:* Expand Open Question #5 (or add a new one) to explicitly require: a documented resolver algorithm with worked examples for (a) year-only source dates, (b) Office discontinuity/replacement, (c) the existence-boundary edge case — and require that `Office` carry its own `establishedOn`/`abolishedOn` fields (note: `Institution` already has these per schema lines 297-298, but `Position` does not — another schema gap).

- **critical** Open Question #3 is correctly identified as "the single biggest determinant" but is framed as a yes/no feasibility check rather than a scoping decision — and the codebase shows the answer is very likely "no, and building it is a multi-month research-grade undertaking" (Open Question #3, FR-7, §11, `seed-political.ts`) — The newly added `prisma/seed-political.ts` (in the current diff) — the team's most recent and most complete attempt at "real political data" — is **exclusively current-day**: "Modi 3.0 cabinet, state CMs, and post-2017 landmark cases" (file header), hardcoded as static arrays of *currently serving* people with no `validFrom`/historical rows. This is strong evidence that **no historical national-tenure dataset exists internally**, and there's no public, machine-readable, single-source national dataset of "who held which Union Cabinet / central-institution post on any given day from 1947–present" — ADR/MyNeta covers candidates' declared facts at election time (not day-by-day office occupancy), PRS tracks legislative business, and India's own government has no unified historical-tenure API. Realistically this requires manually compiling and cross-verifying ~75 years of Lok Sabha/Rajya Sabha records, Gazette notifications, and Cabinet reshuffle archives — a research project, not an ETL job. Open Question #3 asks "is there a sourced dataset, or does this need new ETL work" as if those are comparably-sized outcomes; they are not. The honest framing is "this dataset almost certainly does not exist in usable form, and assembling+verifying it for just the national layer (President, PM, Cabinet, central institutions, judiciary apex) across ~20 Lok Sabha terms is itself a multi-month sourcing project that should be scoped, staffed, and risk-assessed *before* FR-7 is committed to a release plan." *Fix:* Reframe OQ-3 from a binary availability check into a scoping question: "What is the minimum viable historical depth (e.g., post-1990, or 5 PM transitions) that delivers UJ-2's payoff, and what's the cost/timeline to source-and-verify *that* slice — with 1947 as a stretch goal, not an MVP commitment?" Strongly recommend the PM treat "continuous to 1947" as provisional pending a time-boxed data-sourcing spike, with a documented fallback (e.g., "anchored to known transitions post-1990, thinner/skeleton-only pre-1990") rather than shipping the spec as-is into architecture.

- **high** FR-1 + FR-7 combination ("interactive mobile graph" + "continuous re-render on scrub") asks the stack to do something it has never done, with no stated budget to design against (§4.1, §4.4, FR-1 consequence, FR-7 consequence, Open Question #1, project-context.md lines 28/32/98) — `project-context.md` flags Cytoscape/D3/MapLibre/Recharts as either having "zero active imports" (D3, MapLibre, Recharts) or, in Cytoscape's one live usage (`PoliticalRelationshipMap.tsx`), rendering a small **static** preset-position layout (~3 alliance/party node groups, fixed `CYTOSCAPE_ELEMENTS`, no live re-layout, loaded via lazy `import("cytoscape")`). There is **no precedent anywhere in this codebase** for (a) a graph that re-fetches and re-lays-out on a continuous input change (a drag gesture firing many times per second), (b) doing so with photo-bearing person nodes (image loading/decoding cost per re-render), or (c) doing any of this performantly on mobile touch viewports. FR-7's consequence — "re-rendering completes within the same interactivity budget as the initial graph load (FR-1)" — chains an undefined budget (Open Question #1, explicitly `[ASSUMPTION: TBD]`) into a *harder* problem (incremental re-layout vs. cold load) and calls it equivalent. Debounncing/throttling the scrubber, choosing a re-layout strategy that doesn't jitter node positions on every frame, and keeping 60fps-ish drag feedback on a mid-range Android phone while photos repaint is a substantial new engineering investment — closer to "prototype a mobile graph-rendering approach from scratch" than "wire up the viz lib that's already in package.json." *Fix:* Either (a) explicitly scope a pre-architecture technical spike to prototype continuous-scrub graph re-rendering on a representative mobile device and set the performance budget from *that* prototype's findings (not invent a number in the abstract), or (b) soften FR-7's interaction model in the PRD itself — e.g., snap-to-known-transition scrubbing (which the decision log shows was explicitly *rejected* in favor of "continuous") as a fallback the PM should be told is now back on the table given the rendering-cost reality.

- **high** FR-8's assumption that Search reuses `/api/search` glosses over the fact that graph-aware search is a structurally different retrieval problem (§4.5, FR-8, Open Question #4, §11) — `/api/search` (`src/app/api/search/route.ts`, `src/lib/search/retriever.ts`) is an Elasticsearch hybrid BM25+KNN pipeline over **document domains** (`constitution`, `representative`, `institution`, `election`) with intent classification and RRF merging — it returns ranked content hits, not graph-coordinate-addressable nodes scoped to a point in time. FR-8 needs something categorically different: "find entity X, resolve which `Tenure`/Node-state is active as of the *currently-scrubbed* date, and return enough graph-position metadata (parent/child edges, layout coordinates or an anchor to compute them) to center the view there without losing Time Travel state." That's a graph-traversal+temporal-resolution query against Neo4j/Postgres (likely via `GraphService`/`DiscoveryService`), not an ES document search — at best `/api/search` could supply the *name-matching* front-end (autocomplete over `representative`/`institution` domains), with a wholly separate resolution step to map a search hit to "the Node/Tenure active on date D, plus its position in the currently-rendered graph." The PRD's framing — "Search returns results within LokTantra's existing search-route conventions… [ASSUMPTION: reuses `/api/search`]" — understates this: it's not a question of *which endpoint* serves the request, it's that the request shape itself (entity + as-of-date + graph-position) doesn't fit the existing endpoint's contract at all. *Fix:* Sharpen Open Question #4 from "does it reuse `/api/search`?" to "Search-to-graph resolution is a two-step problem (1: name/entity matching — may reuse `/api/search`'s ES indices; 2: temporal+graph resolution to a renderable Node — needs a new graph-service method). Architecture should design the second step as new work, not assume the existing endpoint covers it."

- **medium** FR-7's per-date re-render breaks the existing civic-page caching model without the PRD acknowwledging a new caching strategy is needed (§4.4, FR-7, project-context.md line 100, `next.config.mjs` cache tiers) — `next.config.mjs` defines a cache tier for `/(constitution|parties|elections|judiciary|power-structure)` (`public, max-age=60, s-maxage=300`) and for `/api/(parties|timeline|institutions|judiciary|graph/:path*)`. Both models assume a small, near-static set of cacheable states. Power Explorer's graph state is parameterized by an effectively continuous date input (`1947-08-15` .. today = ~28,000 distinct days × however many distinct Office/Tenure combinations), which means either (a) the cache key space is unbounded and CDN/edge caching for this route provides near-zero hit rate (every distinct date = a cache miss, defeating `s-maxage`), or (b) the team needs a fundamentally different caching strategy (e.g., cache by *Tenure-transition interval* rather than by date, since "last known state" means whole ranges of dates resolve identically). The PRD doesn't surface this, and it has real backend-load implications: combined with `project-context.md`'s flagged gap that "public civic pages have no `revalidate` — every request hits the DB," a Power Explorer that re-queries on every scrub-frame could generate substantially more DB/Neo4j load than any existing page. *Fix:* Add a consequence to FR-7 (or an architecture note) that re-render queries must be designed around Tenure-*interval* caching (cache key = active-Tenure-set-hash, not raw date), and that the scrubber UI must debounce/throttle requests rather than firing one per drag-frame.

- **medium** FR-1's "vacant"/"unknown" display states and FR-7's "not yet established" states both assume the data model can represent absence-with-reason, but nothing in the schema currently encodes *why* a field is empty (§4.1 FR-1 consequence, §4.4 FR-7 consequence, Open Question #5) — `Position.currentHolderId` is a nullable `String?`, and `Person` fields like `photoUrl`/`thumbnailUrl` are nullable with a separate `mediaVerified: Boolean` flag — but there's no encoded distinction between "this Office is vacant right now" vs. "we don't have data for who held this Office on this date" vs. "this Office didn't exist on this date." All three currently look identical at the data layer (null/missing row), yet FR-1 and FR-7 each demand the UI render a *different, explicit* message for what is structurally the same "no row" condition. Open Question #5 names this gap correctly but frames it as a single yes/no ("does the model support the distinction") when it's actually three distinct states needing three distinct schema-level signals (e.g., an `Office.establishedOn`/`abolishedOn` pair to compute "not yet established"/"abolished," a `Tenure.status` enum or explicit `vacantFrom`/`vacantTo` rows to encode genuine vacancy, and a separate "no data for this period" signal that is *not* the same as "vacant" — important because conflating "we don't know" with "nobody held this post" would itself be a neutrality/accuracy problem given §5's guardrails). *Fix:* Expand Open Question #5 into three explicit sub-states the data model must represent (vacant / not-yet-established-or-abolished / data-not-available-for-period), and note that the third state is itself a new requirement this PRD introduces (current schema has no "data confidence/completeness" signal anywhere), with real implications for how "last known state" should *visually* communicate uncertainty for sparse pre-1990s periods.

- **low** The "replaces `/power-structure` outright" framing (§6, Open Question #2) undersells the magnitude of the cutover given how much heavier Power Explorer's data dependency is — `PowerHierarchyExplorer.tsx` (561 lines) is a static institutional-tree component reading from what is, by the PRD's own description, "current office-holder only" data — i.e., it can ship and run today on the *existing* `Position.currentHolder` 1:1 relation with no historical model. Power Explorer cannot reach feature-parity with even that simple page until the new `Office`/`Tenure` schema, historical dataset, and graph-rendering pipeline all exist — meaning the "replacement" isn't a swap-in-place but a long parallel-build-then-cutover, and the old route needs to survive (not be deprecated) for the entire build window. This is implicitly true but never stated, and it changes how architecture should sequence the migration (e.g., feature-flagged dual-running, not a flag-day cutover). *Fix:* Add a note to Open Question #2 that the migration is necessarily a long-running parallel-build (old route stays live and supported until Power Explorer reaches at least FR-1/FR-2 parity on *current* data — historical depth can land incrementally after cutover), not a single retirement event.
