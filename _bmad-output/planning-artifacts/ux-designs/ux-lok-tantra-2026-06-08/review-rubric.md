# Spine Pair Review — Power Explorer UX

## Overall verdict
This is a strong Fast-path draft: both files are in canonical shape order, the inheritance story (extending LokTantra's Tailwind theme rather than inventing a system) is coherent and consistently executed, both UJs have full named flows with climax and failure paths, and the neutrality/accessibility guardrails from the PRD are operationalized into testable visual and behavioral rules rather than restated. The pair is *not* yet a clean source-extraction contract, however: a cluster of `{}` cross-references in DESIGN.md point at paths (`navy.50`, `saffron.500`, `chakra.400`, etc.) that don't exist anywhere in this file's own frontmatter token tree, two color tokens (`state-occupied`, `state-not-established`) ship without resolvable hex values, and the component inventory has a real mismatch (Search and Profile sheet have no DESIGN.md visual-spec row; `party-tag-chip` and `state-badge` have no EXPERIENCE.md behavioral row; "Node" is one row in EXPERIENCE but two distinct cards in DESIGN). A downstream consumer extracting mechanically would stub or mis-resolve several of these.

## 2. Token completeness — thin
Checked: every token in DESIGN.md's YAML frontmatter (`colors`, `typography`, `rounded`, `spacing`, `components`) against the type rules in design-md-spec.md, and every `{path.to.token}` reference in both files' prose/tables for resolution against DESIGN.md's actual frontmatter tree.

### Findings
- **critical** `state-occupied` and `state-not-established` are defined in `colors` (DESIGN.md:31, 33) as descriptive prose strings — `"node's own register color, full opacity"` and `"node's own register color at 20% opacity, dashed outline — absence rendered as absence"` — with **no hex value**, violating the spec's "flat object, kebab-case keys → hex strings" rule for `colors`. `state-vacant` (DESIGN.md:32) at least pairs its description with a literal hex (`#9ca3af`); these two don't. A code-generation consumer cannot resolve either token to a paintable value. *Fix:* either give both a literal hex (even if computed at render time as "register color × opacity," the frontmatter should still carry the base value and the opacity/treatment as separate, resolvable sub-values), or restructure as `components`-style nested objects (`{ base: '{node-person}', opacity: '1.0' }` / `{ base: '{node-person}', opacity: '0.2', outline: 'dashed' }`) so the resolver has something concrete to flatten.
- **high** Eleven `{}`-wrapped cross-references in DESIGN.md's frontmatter — `{navy.50}`, `{navy.900}`, `{navy.500}`, `{navy.300}`, `{navy.200}`, `{navy.700}`, `{saffron.500}`, `{saffron.400}`, `{saffron.300}`, `{chakra.500}`, `{chakra.400}` (DESIGN.md:20-44, e.g. `canvas: "{navy.50}"`, `node-person: "{saffron.500}"`, `scrubber-thumb: "{saffron.500}"`) — use the internal `{path.to.token}` cross-reference syntax to point at paths (`navy.*`, `saffron.*`, `chakra.*`) that **do not exist anywhere in this file's frontmatter** (there is no top-level `navy:`, `saffron:`, or `chakra:` key — those ramps live in `tailwind.config.ts`, an external file). This is exactly the broken-`{}`-reference pattern the spec's "UI-system inheritance" guidance says to avoid by "referencing the system's tokens by name rather than restating values" *in plain prose* — which is what the file correctly does elsewhere (e.g. `tailwind.config.ts (theme.extend.colors)` as a backtick mention). Wrapping an external-system path in `{}` implies it resolves against *this file's* token tree; it doesn't, and a resolver would either error or silently emit `undefined`. *Fix:* drop the braces and render these as plain values/mentions — either restate the literal hex inherited from `tailwind.config.ts` (e.g. `canvas: '#eff6ff'  # = navy.50, see tailwind.config.ts`) or reference them the same way the `inherits` keys and prose already do (plain backtick `navy-50` / `theme.extend.colors.navy[50]` mention, not `{}`). The fix is mechanical and low-risk — but as written, eleven of the file's own frontmatter *values* fail to resolve under its own cross-reference syntax.
- **medium** Inconsistent qualification of `colors` sub-key references in prose: `{typography.headline}`, `{typography.body}`, `{typography.data}`, `{rounded.chip}`, `{rounded.sheet}`, `{rounded.node-card}`, `{spacing.canvas-padding}`, `{spacing.node-min-tap-target}`, `{spacing.sheet-snap-points}` are all fully qualified (`{section.key}`), but `colors` sub-keys are referenced *bare* throughout — `{node-person}`, `{node-office}`, `{node-institution}`, `{edge-citation}`, `{state-vacant}`, `{canvas-dark}`, `{time-marker-approximate}` (DESIGN.md:81, 87-89, 98, 101, 140, 148-153) — never as `{colors.node-person}` etc. The spec's own examples (`{colors.primary}`, `{colors.accent}`) qualify color refs the same way typography/rounded/spacing refs are qualified here. These bare refs *do* resolve (there's no other `node-person` etc. anywhere in the frontmatter to collide with), so they aren't strictly broken — but the inconsistency means a resolver written to the spec's documented pattern (`{section.key}`) would fail on every color reference in this file while succeeding on every other token type. *Fix:* prefix all bare color refs with `colors.` for consistency with the rest of the file's own (correct) qualification discipline — `{colors.node-person}`, `{colors.edge-citation}`, etc.
- **low** `EXPERIENCE.md` carries a bare `{time-marker-approximate}` reference (EXPERIENCE.md:71) with the same qualification gap as #3 above — it should be `{colors.time-marker-approximate}` once DESIGN.md's own refs are normalized, so the two files stay mechanically consistent. `{spacing.canvas-padding}` (EXPERIENCE.md:103) is correctly fully-qualified and resolves cleanly — it's the one EXPERIENCE.md cross-ref that's unambiguously clean.
- **low** `edge-base` / `edge-base-dark` (DESIGN.md:28-29, hex `#94a3b8` / `#475569`) are fully defined with literal hex values but **never referenced or explained anywhere in the body** — every other edge mention routes through `{edge-citation}`. This isn't broken (the token is complete and resolvable), but a reader can't tell from the prose what a non-citation-bearing edge's color *is* — DESIGN.md → Shapes (line 140) describes edges as "directional… arrowhead… labeled" but never states their base color, leaving `edge-base` orphaned. *Fix:* add one clause to the Shapes or Components edge description naming `{edge-base}` as the default edge stroke color (the value clearly exists for exactly this purpose; it's just not connected to its own description).

Note: as instructed, the `tailwind.config.ts`, `theme.extend.colors`, `theme.extend.fontFamily` backtick/plain-text mentions throughout (DESIGN.md:19, 46, 51, 56, 73, 105, 109, 115, 128) are correctly *not* `{}`-wrapped — that pattern is intentional and correctly executed; it is the `{navy.*}` / `{saffron.*}` / `{chakra.*}` instances specifically (which mix the external-reference intent with internal cross-ref syntax) that are the problem.

## 3. Component coverage — thin
Checked: every component name used anywhere in either file against DESIGN.md → Components (visual spec row) and EXPERIENCE.md → Component Patterns (behavioral row).

### Findings
- **high** `Search` (named as an IA surface and given a full Component Patterns behavioral row at EXPERIENCE.md:61: "Opens as an overlay; results respect the active Time Travel date and are paginated/debounced…") has **no DESIGN.md visual-spec row at all** — it doesn't appear in the Components table, and a body-wide search confirms the string "search" never occurs anywhere in DESIGN.md. A consumer building the Search overlay has zero visual guidance: no specified surface treatment, no token bindings, nothing. *Fix:* add a `search-overlay` (or similar) row to DESIGN.md → Components specifying its surface (sheet? full-bleed overlay? inline chrome element?), corner radius, typography roles for query/results, and how result rows render (presumably echoing `node-card-person`/`node-card-office` treatments, but that echo needs to be stated, not assumed).
- **medium** `Profile sheet` (EXPERIENCE.md:58, with a full behavioral row: "Opens at the **half** snap point; drag to peek/full/dismiss…") has no matching named row in DESIGN.md → Components. DESIGN.md only describes "sheets" generically in prose (Layout & Spacing line 118: "`{spacing.sheet-snap-points}` — profile/citation/Accountability sheets snap to peek/half/full…"; Shapes line 141: "**Sheets** use `{rounded.sheet}`…") and gives `citation-panel` its own dedicated Components row but not a `profile-sheet` counterpart. Since the profile sheet is the single highest-traffic overlay in the product (it's what both UJ-1 and UJ-2 open), its visual spec deserves its own named row alongside `citation-panel` and `accountability-block` — not just shared generic "sheet" prose. *Fix:* add a `profile-sheet` row to DESIGN.md → Components naming its anatomy (header treatment, photo/name placement, section ordering for career path / office powers / Accountability) the same way `citation-panel`'s row does.
- **medium** `party-tag-chip` and `state-badge` each have a full DESIGN.md visual-spec row (lines 151, 155) but **no corresponding row in EXPERIENCE.md → Component Patterns** — there's no behavioral spec for what happens when a user taps a party tag (does it do anything? filter? nothing?) or how a state badge behaves across surfaces (does it appear identically in graph and profile, does it animate on state-transition during Time Travel scrubbing?). Both are small components, but "real rules, not one-word descriptions" is the bar the rubric sets, and right now their behavioral half is simply absent rather than thin. *Fix:* add two rows — even brief ones (e.g., "party-tag-chip: non-interactive, decorative-factual only, never tappable — binds §5's 'color is secondary' guardrail" / "state-badge: re-renders on every `time-rewind` tick, label text changes synchronously with the badge shape, never a separate async load").
- **low** Naming-granularity mismatch: DESIGN.md names two distinct cards, `node-card-person` and `node-card-office` (each with its own visual-spec row, lines 148-149), while EXPERIENCE.md collapses both — plus Institution — into a single Component Patterns row, "**Node (Person / Office / Institution)**" (line 56). This isn't strictly *broken* (the behavioral rule given — "Tap → expands in place via `graph-traverse`" — does plausibly apply to all three), but it means a consumer cross-referencing by name won't find `node-card-person` or `node-card-office` in EXPERIENCE.md, nor will they find a row named simply "Node" in DESIGN.md. Institution in particular gets a color register (`{node-institution}`) and a passing mention inside `node-card-office`'s spec ("Rounded square, `{node-office}` **or** `{node-institution}` register…") but no visual-spec row of its own — its card is implied to be structurally identical to `node-card-office`'s, which may well be the right call, but the spine should say so explicitly rather than leave it inferable. *Fix:* either split EXPERIENCE.md's row to mirror DESIGN.md's two (plus a one-line note that Institution shares Office's card template), or rename DESIGN.md's rows to a shared `node-card` family name that EXPERIENCE.md's single row can cleanly reference.

## 4. State coverage — adequate
Checked: every IA surface in EXPERIENCE.md → Information Architecture (Power Graph, Person/Office profile sheet, Citation panel, Time Travel scrubber, Search) walked against the plausible state set for an unauthenticated-friendly, read-only, no-permissions product (empty, cold-load, focus, error/offline, loading-in-flight — permission-denied is correctly N/A throughout and isn't expected to appear).

### Findings
- **medium** `Person/Office profile sheet` and `Citation panel` have no **cold-load / in-flight-fetch** state of their own. The State Patterns table covers cold-open for the *graph* (line 68) and connectivity failure for the *graph* (line 74), but once a Node is tapped, the profile sheet and citation panel presumably need to fetch their own data (career path, Office powers, Accountability Data, citation explainer text) — and the spine is silent on what renders while that's in flight, or if that fetch fails independently of the graph's own load state. Given FR-3/FR-4/FR-5/FR-6 are the profile sheet's entire payload, this is a real, plausible gap a story-writer will hit immediately. *Fix:* add two rows — "Profile sheet loading" (e.g., skeleton rows inside the sheet, sheet still opens at half snap point immediately so the user's tap registers) and "Profile/citation fetch failure" (does the sheet show an inline error and stay open, or close back to the graph?).
- **medium** `Search` has no **idle/empty-query** state (what does the overlay show the instant it opens, before the user types anything — recent searches? a prompt? nothing?) and no **in-flight/debounce-pending** state (PRD explicitly calls out "paginated, debounced" — so there *is* a window between keystroke and results where something must render). Only "no results" (line 73) is covered. *Fix:* add "Search — idle" (overlay just opened, no query yet) and "Search — pending" (debounce window, spinner or skeleton rows) rows.
- **low** `Time Travel scrubber` has no explicit **"scrub in flight" / re-render-pending** state distinct from the committed `time-rewind` re-render. FR-7's consequence "re-rendering completes within the same interactivity budget as initial load" implies there *is* a window — possibly long enough on mobile to need its own treatment — between drag and settled graph, and the spine doesn't say what the canvas shows mid-drag versus mid-settle (current Nodes frozen? already morphing? a loading veil?). This is adjacent to the Open Question #1 performance spike the PRD calls out, so it may be legitimately deferred — but as written it reads as an omission rather than a flagged defer. *Fix:* either add a one-line "Scrub in progress" row (even if it's `[ASSUMPTION — pending Open Question #1 spike]`), or explicitly note in the existing `time-rewind` row that the in-flight visual is intentionally left to the spike's findings.
- **low** No **keyboard/input "focus" visual state** appears anywhere in State Patterns (the only "focus" language in EXPERIENCE.md is *accessibility focus-traversal behavior*, line 96 — a different concept from a visually-styled focused-element state). For a touch-first canvas product this is a minor gap — there's no text input on the graph itself — but Search *does* have a text field, and its focused-state appearance (e.g., does the overlay's input get a visible focus ring per `DESIGN.md`'s tokens?) goes unaddressed. Low severity given the product's touch-first posture, but worth a one-line mention for the desktop/keyboard path the Responsive & Platform section already opens up.
- **Cold open, Vacant Office, Not-yet-established/discontinued, Approximate historical date, Missing Accountability Data, Search-no-results, Fetch/connectivity failure (graph-level), and Reduced motion** are all explicitly covered with concrete, testable treatments and microcopy — strong work on the surfaces and states the PRD makes load-bearing (FR-5, FR-7's three Office-states, the neutrality-driven microcopy rules). The gaps above are in the *peripheral* loading/empty states around overlays, not in the product's signature states.
